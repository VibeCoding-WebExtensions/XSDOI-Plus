# 构建与发布

## 版本号规则

| 改动类型 | 递增 |
|---|---|
| 更新功能 / 修 bug（含「在已有功能上改动」）| patch：`a.b.c → a.b.(c+1)` |
| 全新功能 / 全新面板 | minor：`a.b.c → a.(b+1).0` |
| major | **只在用户明确要求时** |

tag / commit 标题统一**大写 V**（`V4.6.3`）。

## 自动发版流程

推送到 `main` 即触发 `.github/workflows/pack-crx.yml`：

```
读 manifest 版本号
  → 写入 PEM 私钥（仓库 secret CRX_PRIVATE_KEY）并校验
  → 用 Chrome --pack-extension 打包 crx
  → verify-crx.py 校验产物
  → 打源码 zip + 断言必需文件齐全 + 校验全部文本文件是合法 UTF-8
  → 发 Release（tag = V{manifest 版本}，同名 tag 复用同一个 Release 并替换 asset）
```

也可以在 Actions 页面手动 `Run workflow` 重跑，不必提交一次。

### 扩展 ID 是恒定的

`nbcjlcfddbmniidbmpbpagdcpaeoofec`

由**私钥**决定：sha256(公钥 SPKI DER) 前 16 字节，每个 nibble 映射到 `a`-`p`。

⚠️ **secret 放错钥匙时打包不报错** —— 会静默打出一个同名但**另一个 ID** 的扩展。所以 `verify-crx.py` 里有一句**硬断言**：crx 内嵌公钥推出的 ID 必须等于上面这个值，对不上就让构建失败。这是唯一能拦住它的检查。

### 仓库 secret

`Settings → Secrets and variables → Actions → New repository secret`，名字必须叫 `CRX_PRIVATE_KEY`，内容是 `XSDOI-Plus.pem` 做 base64 后的字符串。**私钥绝不能进仓库**（公开仓库泄露私钥 = 任何人可签出同 ID 的 crx），`.gitignore` 已挡 `*.pem` / `*.b64` / `*.crx`。

## 产物

| 文件 | 用途 |
|---|---|
| `XSDOI-Plus.crx` | 自动打包 / 校验用。**不能直接安装** |
| `XSDOI-Plus-<版本>-source.zip` | 给用户：解压后在扩展管理页「加载已解压的扩展程序」，选 `XSDOI-Plus/` 文件夹 |

源码 zip 的顶层目录固定叫 `XSDOI-Plus/`（比 GitHub 自动生成的 `XSDOI-Plus-main-<短SHA>/` 好选），内容与 crx 对齐（同样跳过点开头的条目）。

## 分发禁忌

### ⚠️ 别把 `.crx` 改名成 `.zip` 再解压

**crx 不是 zip** —— 前面有 593 字节的签名头（`Cr24` + 版本 + 公钥长度 + 公钥）。解压工具按 zip 中央目录里记录的**绝对偏移**定位，偏移少了 593 → **条目全部读错位**，解出来的文件是坏的。

### ⚠️ 扩展里的 `.js` 必须是合法 UTF-8

非 UTF-8 的扩展 JS 会被 Chrome / Edge **直接拒绝加载**：

```
无法为内容脚本加载"constants.js"文件。该文件采用的不是 UTF-8 编码。
→ service worker target 数 = 0   ← 后台脚本根本没起来
```

扩展卡片上只显示一句**「无法加载背景脚本」**，真实原因藏在错误详情里，极难定位。`constants.js` 之所以先炸，是因为它同时列在 `manifest.json` 的 `content_scripts` 里，Chrome 先在那儿校验。

- 这跟 Windows 有没有开「使用 Unicode UTF-8 提供全球语言支持」**无关** —— Chrome / V8 一律按 UTF-8 解析扩展资源，那个系统开关只影响 PowerShell / 批处理 / csc 这类 **Windows 原生程序**。
- 要出问题必须是**文件被按 ANSI/GBK 另存过**（用记事本或某些编辑器打开再保存、解压工具带转码选项）。
- CI 每次发版都会校验全部 `.js` / `.json` / `.html` / `.css` 是合法 UTF-8，不通过就让构建失败。

### 最低浏览器版本：`minimum_chrome_version: "102"`

代码自动备份用 OPFS（`navigator.storage.getDirectory()`），硬门槛是 Chrome / Edge 102。声明之后，版本不够时浏览器会直接给「需要 Chrome 102 以上」这种能看懂的提示，而不是只抛一句「无法加载背景脚本」。

## 自托管 crx 没有自动更新通道

Chrome 只对**商店上架**的扩展走自动更新，本项目 manifest 里没有 `update_url`。所以 popup 的「检查更新」栏目只做**检测 + 引导**：

- fetch `api.github.com/repos/VibeCoding-WebExtensions/XSDOI-Plus/releases/latest`，比对 `tag_name` 与 `chrome.runtime.getManifest().version`
- 三种状态：已是最新 / 发现新版本 / 本地是开发版（本地版本高于线上）
- 「打开发布页」按钮**常驻**，指向 `github.com/<repo>/releases/latest`（这个指针链接永远 302 到当前最新 tag 的 Release 页，不依赖检测结果），所以检测失败时也能点进去下载

**别加「一键下载 crx」**：那要多申请一个 `downloads` 权限，但 Chrome 不允许安装非商店来源的 crx，最后仍要解压后「加载已解压的扩展程序」，白加一个权限。

## 本地手动打包（备用）

CI 之外想在本机出 crx，用仓库里的 `XSDOI-Plus.pem`：

```bash
"C:/Program Files (x86)/Microsoft/Edge/Application/msedge.exe" \
  --pack-extension="<扩展目录绝对路径>" \
  --pack-extension-key="<XSDOI-Plus.pem 绝对路径>" \
  --no-message-box
```

产物落在扩展目录的父目录，文件名取目录名（`XSDOI-Plus.crx`）。

> 本地 crx 与 CI crx **字节大小对不上是正常的**（差一百来字节），crx 打包不是字节可复现的，别拿大小 / hash 比对。
